## Известные ограничения и следующий ограниченный шаг

Прямолинейный AI может застревать у укрытий; навигации нет. Арт геометрический. Щит миньона использует обычную всенаправленную броню15, фронтальная форма визуальная. Перенос ресурсов не сохраняет незавершённый reload. Нет подтверждённых показателей производительности Stage2. Локальный измеритель фиксирует интервал кадров с frame pacing, а не изолированный CPU frame time; обновление списка пулов раз в секунду и сам прибор влияют на измерение. Его запуск не удостоверяет прохождение маршрута. Подготовленные инструменты ещё требуют проверки; в частности абсолютный output path сам по себе не гарантирует нахождение внутри проекта, поэтому при будущем запуске явно задавать каталог в `Game/TestResults/`. Отсутствующую GC-метрику следует обозначать unavailable, а не измеренным нулём.

Следующий предлагаемый шаг ограничен закрытием Mac Editor-регрессии текущей рабочей копии: сначала три новые проверки босса/стрелка, затем полные EditMode/PlayMode (ориентир42/84) с новой парой XML, после этого ручной Bootstrap-маршрут Stage2 и контроль Stage1. Записать фактические counts, версию и исполнителя в статус У1. Исправления кода пока остаются незакоммиченными и не входят в чистую checkout-версию этого итогового коммита; проверять именно документированный рабочий diff. Затем отдельным поручением завершать сборки/Player/устройства из таблицы. Генератор, сохранения, экономика и монетизация не начинаются.

Это пробел инструмента, а не доказанный отказ Android-игры.
3. `createdProjectiles` в `Stage2Measurements.LateUpdate` — сумма текущих `ProjectilePool.TotalCount`, не накопительный счётчик созданий за попытку. При выгрузке старого пула значение теряется; список пулов обновляется раз в секунду и может временно пропустить новый пул. Перед замерами уточнить название/смысл метрики либо добавить настоящий счётчик и проверить смену арены с активными пулями. Не трактовать имеющиеся поля как измеренный общий объём спавна или гарантированный пик.
4. `errors` прибора охватывает время после подписки в Start и только до однократной записи JSON. Ошибки до подписки и после записи в экспорт не попадут. Поэтому приёмка запуска обязана сверять полный Player-лог; `errors=0` внутри measurements не означает отсутствие ошибок всего запуска.
5. `Setup/Stage2/run_validation.py`, строка12: проверка существующего lock вызывает `lsof` без проверки доступности команды/OS; на Windows без этой утилиты helper остановится до тестов. Его сборочная проверка, строки46–49, сверяет exit/result/errors, но не точный список сцен, платформу/версию и наличие выходного Player. До заявления о межплатформенном helper добавить проверку этих условий либо дать отдельные проверенные команды для каждой платформы. XML-проверку дополнить согласованием итоговых счётчиков с узлами и проверкой полного состава набора.
6. Старые формулировки общего плана/плана сборок ещё говорят «не реализовано», «только Stage1» и40/84; это исторические записи. После фактического выполнения остатка добавить актуальный итог и пути доказательств, сохранив историю У2. Не переписывать прежние неуспешные прогоны в успешные.
