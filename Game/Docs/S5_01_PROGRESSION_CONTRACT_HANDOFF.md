# S5-01. Передача контракта экономики от У1 к У2

Ветка `feat/stage5-progression`, база `ee71a09`. Контракт доступен в `Game.Runtime` через `Game.Contracts.IProgressionSession`. [Команды и типы ключей](../Assets/_Game/Scripts/Contracts/IProgressionSession.cs) · [Снимки](../Assets/_Game/Scripts/Contracts/ProgressionSnapshots.cs) · [Контрактные тесты](../Assets/_Game/Tests/EditMode/ProgressionContractTests.cs)

Можно подключить тестовый адаптер У2 к интерфейсу и воспроизвести приведённые ниже снимки. Добычу и действия NPC реализует У1 в S5-03. Запись профиля и восстановление приходят в S5-05. Снимки показывают данные для UI, тексты сообщений и положение объектов на сцене задаёт У2.

## Ключи и результаты

Команда получает `ProgressionCommandKey(RunId, ActionId)`. В Home передаётся `RunId = null`, а пространство ключей относится к текущему профилю. Сравнение ID порядковое, с учётом регистра. ActionId уникален среди команд одного забега либо одного профиля для Home. Сохраняйте ключ и параметры до окончательного результата. Для смерти и зачистки подходят воспроизводимые ActionId, полученные из SpawnId и checkpointIndex, например `death:combat_a/shooter-2` и `clear:0`. Для действий игрока создавайте ID на одно осознанное подтверждение. Самостоятельные уникальные ключи сущностей для защиты от двойной выдачи — `(RunId, SpawnId)`, `(RunId, checkpointIndex)`, `(RunId, PointId, NpcId, OfferId)` и `(RunId, ItemId)`. Один и тот же подбор с новым ключом может забрать остаток, если он есть.

| Status | Failure | Что получает У2 |
|---|---|---|
| `Applied` | `None` | Команда принята впервые либо завершился допустимый повтор после временной ошибки. |
| `Rejected` | Например, `InsufficientCoins` | Команда завершилась отказом. Выдача, списание и эффект отсутствуют. После изменения условий новое осознанное действие получает новый ActionId. |
| `Replayed` | Причина исходного окончательного отказа либо `None` | Совпали ключ и параметры завершённой команды либо тот же доменный факт смерти или зачистки. Возвращается её исход и текущий снимок. Повторного списания или создания объектов нет. |
| `RetryableFailure` | `SaveFailed` или `ServiceNotReady` | Операция ещё не завершилась. Для повтора отправьте те же параметры и ActionId. |
| `Rejected` | `Conflict` | Вызов повторно использовал ActionId с другой командой или параметрами либо нарушил идентичность доменного факта. Состояние и результат первой команды сохраняются. |

Последовательная обработка команд одного профиля/забега оставляет один окончательный результат для каждого ключа. Временный отказ сохраняет привязку ключа к параметрам, но допускает повторное исполнение. Каждая строка таблицы возвращает актуальный снимок. Синхронизируйте представление по ID записей в снимке и текущему RunId. Одноразовые анимации запускайте по первому `Applied`, а при повторе восстанавливайте видимые объекты по снимку. Отклонение предложения закрывает диалог локально.

## Точки перехода

Форма записи — `new ProgressionTransitionPoint(pointId, stageId, roadId, entranceId, allowedNpcs)`. PointId уникален для каталога City, остальные поля связывают запись с физической геометрией У2. `AllowedNpcs` задаёт допустимые виды через флаги `WeaponDealer` и `BottleDealer`. В план попытки попадают только выбранные для размещения точки. `Run.Npcs` содержит их исходные записи и стабильные NpcId, остающиеся валидными при повторном входе. Координаты входа, интерьера и возврата берутся из каталога карты по ID.

| StageId | PointId | RoadId | EntranceId | Допустимый NPC |
|---|---|---|---|---|
| 1-1 | `1-1/a-to-b` | `a-to-b` | `alley` | `WeaponDealer` |
| 1-1 | `1-1/b-to-c` | `b-to-c` | `house-door` | `BottleDealer` |
| 1-2 | `1-2/a-to-b` | `a-to-b` | `alley` | `WeaponDealer` |
| 1-3 | `1-3/b-to-c` | `b-to-c` | `house-door` | `BottleDealer` |
| 1-4 | `1-4/a-to-b` | `a-to-b` | `courtyard-door` | `WeaponDealer` и `BottleDealer` |
| 1-5 | `1-5/b-to-c` | `b-to-c` | `house-door` | `BottleDealer` |

Первые два PointId совпадают с текущим макетом У2. Идентификаторы дорог и входов в таблице предлагаются для каталога. Строки 1-2…1-5 синтетические и служат для проверки плана пяти стадий. Даже при шести доступных точках в одной попытке размещаются до одного Барыги и двух Диллеров, по одному на точку.

## Примеры для HUD и переходов

Примеры используют `RunId = "city-test-42"` и `ProgressionCheckpoint("1-1", "combat_a", 0)`. Индекс постоянен для конкретной зачистки и уникален за всю попытку. Выдавайте его из маршрута при связывании комнаты. Переход по карте не генерирует новый индекс для посещённой комнаты. Отображаемые цены и количество добычи здесь заданы для теста.

| Событие или действие | Результат | Поля снимка для У2 |
|---|---|---|
| `ConfirmEnemyDeath` для `combat_a/shooter-2`, тип `shooter` | `Applied` | В `Run.Loot` записи с этим SpawnId, например `.../ammo` с `Remaining = 8`, `.../coins` с `Remaining = 2` и `.../crystals` с `Remaining = 6`. Позиция берётся из callback смерти. |
| `CollectLoot` для `.../ammo` при трёх свободных местах в резерве | `Applied` | Тот же PickupId с `Remaining = 5`. Исчезновение записи означает, что забирать больше нечего. `ResourceFull` оставляет запись и количество. |
| `BuyNpcOffer` у Барыги за 3 с балансом 2 | `Rejected / InsufficientCoins` | `Run.Coins = 2`, `PriceCoins = 3`, `State = Offered`. HUD показывает нехватку 1 на первом отказе. |
| `BuyNpcOffer` у Барыги в игровое время 12 с балансом 5 | `Applied` | `Coins = 2`, `State = Working`, `ReadyAtGameTime = 14`, `WeaponInstanceId = "pistol-01"`, `ItemId = null`. |
| `CompleteNpcService` у Барыги по достижении 14 | `Applied` | `State = ItemAvailable`, `ItemId = "module-01"`, `ItemDefinitionId = "fire-rate"`, тот же WeaponInstanceId. `ApplyWeaponModule` меняет состояние на `ItemUsed`. |
| `BuyNpcOffer` у Диллера за 4 с балансом 7 | `Applied` | `Coins = 3`, `State = ItemAvailable`, `ItemId = "bottle-01"`, `ItemDefinitionId = "dealer-bottle"`, `ActiveBottleEffect = null`. После отдельного `DrinkBottle` состояние становится `ItemUsed`, а для длительного эффекта заполняется `ActiveBottleEffect`. |
| `CollectLoot` для кристаллов | `Applied` | `Run.PendingCrystals = 6`, `Profile.ConfirmedCrystals = 120`. HUD показывает отдельно ожидающие и подтверждённые. |
| `ClearCheckpoint`, запись не удалась | `RetryableFailure / SaveFailed` | При `Coins = 2` остаются `PendingCrystals = 6`, `ConfirmedCrystals = 120`. Покажите повтор записи. Удерживайте завершение комнаты для экономики и переход к следующей стадии до результата записи. |
| Повтор `ClearCheckpoint` с тем же ключом, ещё 3 кристалла остались на земле в комнате | `Applied` | `Coins = 2`, `PendingCrystals = 0`, `ConfirmedCrystals = 129`. Остатки кристаллов этой комнаты удалены. Следующий повтор возвращает `Replayed` с актуальным балансом. |

Подсказка о нехватке использует цену и текущий баланс. При `Replayed / InsufficientCoins` баланс мог измениться, поэтому старый отказ следует привязать к прежнему нажатию, а доступность кнопки рассчитать заново. `ReadyAtGameTime` — отметка общих игровых часов сервиса и адаптера в секундах. В Unity используйте `Time.timeAsDouble`, который учитывает паузу через `Time.timeScale`. Готовность услуги проверяет сервис, UI может продолжать показывать ожидание после выхода из интерьера. `CompleteNpcService` вызывается по времени услуги независимо от посещения комнаты. После выдачи предмет остаётся до отдельного действия. Для `ItemUsed` ID и описание предмета сохраняются в снимке, а объект убирается со сцены.

`PendingCrystals` показывает подобранные кристаллы всех неподтверждённых комнат. При успешной зачистке сервис учитывает также кристаллы с земли **этой** комнаты. Неподобранные патроны и монеты остаются доступны до смены сцены. Ошибка записи не меняет состав добычи или подтверждённый баланс. Если разовая запись завершилась успешно, её ключ и начисление должны существовать в одной ревизии профиля.

## Подключение адаптера

Вызывайте `StartRun` с RunId от RunCoordinator, seed и каталогом точек City. Привяжите текущий профиль к сессии. Передайте `EnemyDefeated` от RoomController до `Cleared` той же комнаты. Для призванной слизи учитывайте суффикс SpawnId `/summon/n`. У2 создаёт и обновляет предметы по PickupId, а подбор вызывает `CollectLoot`. Реализация У1 использует существующий `IRunResourceSink` для пополнения резерва и удерживает остаток в снимке. Связь с переходами и порталом остаётся на стороне У2.

Команды NPC получают PointId, NpcId, OfferId из снимка. Подтверждение у Барыги дополнительно передаёт стабильный ID экземпляра оружия. Для Диллера `weaponInstanceId = null`. Первый удачный `FinishRun` возвращает `Run = null` и `LastRun` с итоговыми монетами и заработанными подтверждёнными кристаллами. Итоговые монеты предназначены для экрана результата. Home берёт баланс, открытия и предложения из `Profile`, а покупку вызывает с ключом без RunId. При ошибке записи покупки используется исходный ActionId. При `RecoveredFromBackup` покажите предупреждение. При `IncompatibleSchema` блокируйте запись в текущий профиль, пока игрок явно не выберет отдельный профиль.

## Запуск контрактных тестов

Unity **6000.3.28f1**. Откройте проект `Game`, затем **Window → General → Test Runner → EditMode**. Выберите `Game.Tests.ProgressionContractTests` и нажмите **Run Selected**. Ожидается восемь тест-кейсов. Они проверяют типы, образцы для UI и форму результата. Проверки живого сервиса и записи профиля последуют вместе с реализацией.

Из корня репозитория для пакетного запуска используйте путь к установленному Unity, отличный для каждой машины. Проект должен быть закрыт в интерактивном редакторе. Используйте новое имя XML и лога для отдельного прогона.

```sh
mkdir -p Game/TestResults/S5-01
"/path/to/Unity" -batchmode -nographics -projectPath "$PWD/Game" \
  -runTests -testPlatform EditMode -testFilter Game.Tests.ProgressionContractTests \
  -testResults "$PWD/Game/TestResults/S5-01/EditMode.xml" \
  -logFile "$PWD/Game/TestResults/S5-01/EditMode.log"
```
