# Stage 3 — личный план У1: воспроизводимый маршрут и проверка модулей

Подготовлено 16 ноября 2026. База планирования — main `cc67773`, Unity6000.3.28f1. Это последовательность будущих запросов агенту. Цитаты выполняются только после отправки соответствующего запроса. Stage 3 здесь означает следующий командный этап после Stage 2, по содержанию — пять уличных сегментов из этапа4 `.agent/EXCECPLAN.md`. Результат — маршрут1.1–1.5 с генератором, четырьмя обычными встречами и принятым полицейским в конце.

У1 создаёт чистые правила генерации и проверки данных. У2 создаёт Unity-модули, Core-переходы, UI и собирает игру. До итоговой интеграции обе стороны работают на своих данных и сценах. Общие короткие точки связи — передача интерфейса в начале и передача проверенного генератора в конце. Между ними ждать каждого шага другой стороны не требуется.

План пары — `.agent/START_STAGE_3_ROLE_2.md`. Эти два файла содержат одинаковые исходные договорённости. При уточнении интерфейса записать изменение в передачу и сообщить второй стороне до использования новой версии.

## Предварительный интерфейс для независимой работы

Это проект интерфейса v0.1, который У1 фиксирует в S3-01 перед реализацией. Он описывает данные и алгоритм. Unity-загрузка модулей принадлежит У2.

Namespace `Game.Generation`. `RunGenerator.Generate(int seed, StageCatalog catalog, int generatorVersion, int contentVersion)` возвращает `GenerationResult`. `StageCatalog` содержит стабильные идентификаторы модулей и их описания. `ModuleDescriptor` содержит Id, Kind, целочисленные Width/Height, массив Walkable длины Width*Height, клетки Entry/Exit и SpawnCells. `Cell` содержит X/Y. Kind имеет значения Entry, Combat, Rest, Boss. Все размеры положительные, координаты внутри модуля, индекс массива y*Width+x. Данные на входе копируются или трактуются неизменяемыми, ссылки на изменяемые коллекции наружу не выдаются.

`GenerationResult` содержит Layout, UsedFallback и Diagnostic. `RunLayout` содержит Seed, GeneratorVersion, ContentVersion и ровно пять `SegmentLayout`. В сегменте есть Index1..5 и ModuleId. Индексы1..4 используют Combat, индекс5 — Boss. Entry/Rest — вспомогательные модули вне обязательной пятёрки. Не вставлять дополнительные боевые сегменты из-за наличия этих описаний в каталоге. Обычные модули могут повторяться. Версии входят в результат и журнал, время/Guid/UnityEngine.Random не влияют на выбор.

`LayoutValidator.Validate(RunLayout layout, StageCatalog catalog)` возвращает `ValidationResult` с IsValid и Reasons. Проверяется состав пятёрки, известные Id, размеры/клетки и путь по четырём соседним клеткам от входа к выходу и каждой точке появления, включая точку босса. Диагональные срезы углов отсутствуют. Сетка описывает свободное пространство для центра актора с учётом его радиуса, а не сырые видимые квадраты. Boss-модуль учитывает радиус полицейского2 и его свободную площадку отдельно при авторинге/проверке У2.

Исходные Id каталога — `street_entry`, `street_a`, `street_b`, `street_c`, `street_rest`, `street_boss`. Разные сцены загружаются через раздельные стыки Entry→Exit, мировые координаты комнат не обязаны совпадать. Генератор выбирает последовательность модулей, не собирает непрерывную карту физических соединений. При ошибке случайного подбора допускается максимум20 попыток. Проверенный fallback — a,b,c,a,boss. Если сам каталог или fallback невалиден, вернуть явный неуспех без запуска боя. Конкретное представление неуспеха и полные конструкторы зафиксировать в S3-01 до кода. Никогда не возвращать формально успешный непроходимый маршрут.

## Как работать с запросами

Один промпт — один законченный шаг. Для аудита и передачи достаточно среднего уровня рассуждения, для алгоритма/валидации и ревью — высокого. Выбор модели остаётся в интерфейсе клиента, название в промпте её не переключает. При затруднении сначала сохранять воспроизведение, diff и ошибку, затем повышать уровень диагностики.

В каждом handoff указывать базовый/итоговый hash, явные файлы, точные типы/сигнатуры, пример вызова, настройки, новые GUID, фактические XML и discovered/executed/passed/failed/skipped/inconclusive. NOT RUN остаётся отдельным состоянием. Создать локальный коммит явных путей после diff. Исходные XML/сборки хранятся в новых каталогах, в Git включаются компактные отчёты и исходники. Внешний Unity на Mac использовать по разрешённому пользователем пути.

## 2. S3-03A — генератор чистых данных

> Продолжаем Stage 3, роль1, S3-03A. Веди S3_LAYOUT_PLAN. Реализуй воспроизводимый выбор четырёх Combat и одного Boss по принятому S3-01. Используй собственный источник псевдослучайности с явно стабильным алгоритмом и локальным состоянием. Определи порядок обработки каталога независимо от порядка файлов. Зафиксируй версию алгоритма/контента. Проверь одинаковый seed/каталог/версии, отрицательный и крайние int seed, перестановку каталога, независимость от UnityEngine.Random и нескольких последовательных вызовов, допустимые повторы модулей и фиксированный последний Boss. Набор разных seed должен показывать несколько допустимых маршрутов без требования уникальности для каждого seed. Используй собственный маленький каталог, данные сцен У2 не нужны. Обнови план/статус и подготовь локальный отчёт.

Готовность — одинаковые входы дают одинаковые данные, пятый сегмент всегда Boss. Правила генерации не меняют профиль/боевые ресурсы и не загружают сцены.

## 3. S3-03B — достижимость и конечное восстановление

> Продолжаем Stage 3, роль1, S3-03B. Добавь LayoutValidator и конечный подбор/fallback к генератору. Проверяй реальные клетки входа/выхода/спавнов, закрытый проход, изолированную точку, границы, дубликаты Id, неверные размеры массива и неизвестный модуль. В тестах используй вручную понятные маленькие сетки с ожидаемыми маршрутами. Покажи не больше20 попыток и переход на валидный fallback с диагностикой seed/версий/причины. Невалидный fallback или каталог возвращает явный неуспех. Проверь, что входные данные не мутируют и повтор ошибки не накапливает состояние. Не добавляй обход препятствий для AI в эту задачу. Сохрани S3_03_GENERATION_HANDOFF.md с API, примером успеха/отказа, реальными XML/числами и файлами.

Эта передача открывает финальное подключение генератора У2. У1 может сразу переходить к следующему шагу.

## 4. S3-05 — независимая проверка каталога и сложных случаев

> Продолжаем Stage 3, роль1, S3-05. Подготовь воспроизводимую проверку не менее1000 seed на своём эталонном каталоге. Новые тесты добавляй для конкретных рисков генерации, прежние проверки не ослабляй.

Готовность — У2 получает алгоритм и диагностические примеры, а поздняя проверка его данных занимает один короткий проход.
