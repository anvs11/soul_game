# S1-01: создать общую основу через Unity Hub

Актуализация 2026-11-07: шаг создания и базовой проверки уже выполнен человеком. Этот документ сохранён как инструкция настройки; повторять создание Game/ и Install.ps1 не нужно. Для новых сцен и пустого цикла использовать Game/Docs/S1_01_FLOW_CHECK.md.

Это инструкция для первого шага участника 2. Сейчас в разрешённом корне `C:\Users\user\projects\soul_game` нет Unity-проекта. `.agent/` содержит документацию, будущий проект расположен в `Game/` рядом с ней. Подготовительные исходники находятся в `Setup/S1-01/Template/`, а состояние работы — в `Coordination/ROLE_2_STATUS.md`. Наличие этих файлов не означает успешную компиляцию или готовую передачу S1-01.

## 1. Создать проект человеком

1. Открыть Unity Hub самостоятельно. Установка и запуск редактора вне проекта этой сессией не выполнялись. При отсутствии Hub или редактора установить их вручную; агенту нужен отдельно предоставленный доступ для запуска внешнего Unity.exe.
2. В Installs выбрать **Unity 6.3 LTS, 6000.3.28f1**. Если выпуска нет в списке, открыть [официальную страницу выпуска](https://unity.com/releases/editor/whats-new/6000.3.28f1) и воспользоваться установкой через Hub. Этот реальный выпуск от 3 ноября 2026 года выбран единственным кандидатом; локальная совместимость ещё не подтверждена. Не подменять его другим patch без записи решения.
3. В модулях предусмотреть Android Build Support с Android SDK & NDK Tools и OpenJDK. Для начальной Windows-сборки достаточно доступной поддержки Windows; IL2CPP на этом шаге не обязателен. Существующие модули не переустанавливать без причины.
4. В Projects нажать New project, выбрать редактор **6000.3.28f1**, шаблон **2D (Built-In Render Pipeline)**. Если Hub показывает сокращённое имя «2D», проверить описание Built-In. URP сейчас не требуется; если доступен только другой шаблон, остановить создание и согласовать решение.
5. Задать Project name **Game**, Location **C:\Users\user\projects\soul_game**. Итоговый путь должен быть **C:\Users\user\projects\soul_game\Game**, без второго `Game/Game` и без `.agent/Game`. До Create project проверить, что `Game/` отсутствует. Если появилась существующая папка, сначала осмотреть её; не удалять и не заменять.
6. Не создавать отдельный Unity Version Control-репозиторий: в корне уже есть Git. Дождаться полного первого импорта. Проверить наличие `Assets/`, `Packages/`, `ProjectSettings/ProjectVersion.txt` и строку `m_EditorVersion: 6000.3.28f1`. Не создавать этот файл вручную и не менять его ради обхода проверки версии.

## 2. Установить пакеты и настроить ввод

В Package Manager выбрать Unity Registry. Для каждого пакета сначала проверить In Project, затем при необходимости установить совместимый выпуск, предлагаемый менеджером для этого редактора:

| Назначение | ID пакета |
|---|---|
| Ввод | `com.unity.inputsystem` |
| Unity UI / uGUI | `com.unity.ugui` |
| Unity Test Framework | `com.unity.test-framework` |

Если Test Framework скрыт в списке, использовать Add package by name с его ID, без придуманного номера версии. Уже установленный совместимый пакет сохранить. Не включать preview-пакеты и не обновлять всё подряд.

После Input System принять включение нового backend с перезапуском редактора. Проверить Edit → Project Settings → Player → Other Settings → Active Input Handling: **Input System Package (New)**. Если шаблон содержит собственные зависимости от старого ввода, сначала разобраться с ними; не удалять ресурсы шаблона автоматически.

Менеджер сам создаёт и обновляет `Packages/manifest.json` и `Packages/packages-lock.json`. Это фактическое разрешение зависимостей; проверенной совместимостью оно становится после компиляции и запуска сборки. Конкретные номера заранее не назначены. При ошибке сохранить её текст и не продолжать с фиктивным статусом успеха.

## 3. Перенести подготовленные исходники

Закрыть окно Unity именно этого проекта и дождаться завершения процесса. Из PowerShell в корне репозитория выполнить предварительную проверку:

```powershell
Set-Location -LiteralPath 'C:\Users\user\projects\soul_game'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Setup\S1-01\Install.ps1
```

ExecutionPolicy Bypass здесь действует только на дочерний процесс; глобальная политика не меняется, пользовательский профиль не загружается. Скрипт проверяет наличие проекта, точную версию, объявленные и разрешённые пакеты, закрытый редактор и все конфликты перед записью. Без `-Apply` он только выводит `RESOLVED`, `WOULD_CREATE`, `UNCHANGED` и `PREFLIGHT_ONLY`.

После просмотра результата применить тот же набор:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Setup\S1-01\Install.ps1 -Apply
```

Переносятся четыре `.asmdef`, контракт v0.1 и редакторский отчёт. Скрипт не создаёт Unity-проект, не устанавливает пакеты, не меняет существующие исходники или `.meta`, не запускает редактор. При отличающемся файле он останавливается до копирования. При частичном сбое исправить причину и повторить: совпадающие файлы остаются нетронутыми. Ничего не удалять для повторного запуска.

Открыть `Game/` через Hub. Unity сама создаст `.meta`; их необходимо сохранить и передавать участнику 1. Не открывать `Setup/S1-01/Template/` как отдельный проект и не создавать `.meta` вручную.

## 4. Применить настройки и проверить сборки C#

После компиляции вызвать **Game → Setup → Apply serialization settings**. Команда устанавливает Force Text и Visible Meta Files; принудительная пересериализация ресурсов не выполняется. Проверить в Edit → Project Settings: Editor → Asset Serialization → Mode = Force Text; Version Control → Mode = Visible Meta Files. Названия разделов можно найти поиском Project Settings.

Вызвать **Game → Setup → Print baseline**. Console должна показать реальную версию редактора, Serialization: ForceText, Meta: Visible Meta Files, Runtime: Game.Runtime, три фактические версии пакетов и Input System enabled: True. Это отчёт среды, а не доказательство готовой сборки.

`Game.Runtime.asmdef` находится в Scripts/ и включает Contracts/ и будущий игровой код. Отдельная `Scripts/Editor/Game.Editor.asmdef` исключает редакторский код из игрока. Tests/EditMode ограничена Editor; Tests/PlayMode не имеет этого ограничения. Обе используют TestAssemblies. Сейчас тестовых методов нет; отсутствие найденных тестов не считается успешным прогоном. Поведенческие тесты добавляются вместе с механиками.

При ошибке reference сначала проверить завершение установки Input System, Unity UI и Test Framework, затем имена сборок: **Unity.InputSystem**, **UnityEngine.UI**, **Game.Runtime**, **Game.Editor**. Не путать ID пакета `com.unity.ugui` с именем C#-сборки `UnityEngine.UI`. Не удалять Library/ или `.meta` как автоматическое исправление.

## 5. Проверить базовую Windows-сборку и только затем фиксировать версии

Это техническая проверка основы. Пустой цикл Home → CombatSandbox → Home создаётся следующим шагом роли и пока отсутствует.

В редакторе создать новую Basic (2D) сцену и сохранить как `Assets/_Game/Scenes/BaselineSmoke.unity`, сначала проверив отсутствие этого имени. Достаточно камеры; пустой фон ожидаем. Исходную SampleScene не удалять и не заменять.

Через File → Build Profiles выбрать Windows и включить в список сцен только BaselineSmoke. Создать новую папку `Game/Builds/Baseline/Windows/<уникальный buildId>/`, выполнить Build и запустить полученный exe. Ожидаются успешный BuildReport, окно приложения с фоном камеры и отсутствие ошибок компиляции. Пустое окно не является готовым игровым циклом. Старые сборки не перезаписывать. Эта сцена не входит в будущую итоговую сборку первой стадии.

После успешного запуска создать `Game/Docs/TECH_BASELINE.md` с фактическими полями: editor, template, Input System, Unity UI, Test Framework, состояние Active Input Handling, Force Text/Visible Meta Files, buildId, результат сборки и запуска, проверявший человек, непроверенное. Приложить компактный отчёт Game/Setup. При провале записать ошибку и статус «совместимость не подтверждена».

Сохранить фактические `ProjectVersion.txt`, `manifest.json`, `packages-lock.json`, ProjectSettings и все `.meta`. Номера брать только из проекта и Package Manager. Дальше оба участника используют именно эту версию основы без самостоятельного обновления пакетов. Коммит — отдельное действие после просмотра явного списка файлов; эта инструкция его не выполняет.

## 6. Условие передачи участнику 1

Этот шаг завершает подготовку среды только после запуска сборки. Для полной S1-01 ещё требуются Bootstrap, Home, CombatSandbox, GameBootstrap, SceneFlow, RunCoordinator, HomeScreen, описание контракта и десять повторов пустого цикла. Это следующий шаг START_ROLE_2.md; здесь эти сцены не объявляются созданными.

После проверки передать один проект с `Assets/` и `.meta`, `Packages/`, `ProjectSettings/`, документацией и идентификатором общей основы. Кэш, LocalState, TestResults и Builds исключены из Git. Локальный коммит сам по себе не переносит файлы второму человеку; выбрать общий коммит или согласованный перенос. Участник 1 не создаёт второй Game/ и начинает S1-02 после принятия S1-01.
